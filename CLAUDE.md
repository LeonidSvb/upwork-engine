# Инструкции для Claude AI Assistant

## О проекте
Это репозиторий с шаблонами кода и примерами для различных задач разработки.

## Основные правила работы

### Язык общения
- Всегда отвечай на русском языке
- Информацию для клиентов предоставляй на английском
- Внутреннюю документацию и инструкции пиши на русском

### Работа с данными
- Используй только реальные данные, никогда не используй тестовые данные без явного запроса
- При тестировании всегда используй реальные данные

### Веб-запросы
- Для просмотра информации с сайтов используй только HTTP фетчинг
- НЕ используй firecrawl или другие сторонние сервисы скрапинга

### Git и GitHub
- НИКОГДА не делай коммиты на GitHub без прямого указания
- Перед коммитом всегда спрашивай разрешение
- При создании коммитов следуй установленным конвенциям

### Стиль кода
- Не используй эмодзи при написании скриптов
- Следуй существующему стилю кода в проекте
- Комментарии в коде пиши на русском языке

## Основные принципы разработки

### Простота прежде всего (Simplicity First)
- Всегда предпочитай простые решения сложным
- Избегай overengineering и преждевременной оптимизации
- Выбирай понятные реализации, которые легко понять и поддерживать

### DRY (Don't Repeat Yourself)
- Избегай дублирования кода везде, где возможно
- Перед написанием нового функционала проверяй наличие похожего существующего кода
- Рефактори общие паттерны в переиспользуемые утилиты или компоненты
- Разделяй логику между компонентами вместо её дублирования

### Осознание окружения (Environment Awareness)
- Пиши код, который работает одинаково в разных окружениях: dev, test, prod
- Используй переменные окружения для различий в конфигурации
- Избегай хардкода значений, которые могут отличаться между окружениями
- Тестируй поведение кода во всех целевых окружениях

### Фокусированные изменения
- Делай только те изменения, которые запрошены или напрямую связаны с текущей задачей
- Будь уверен, что изменения хорошо поняты и необходимы
- Избегай расширения scope или касательных улучшений без явного запроса

### Консервативный выбор технологий
- При исправлении багов сначала исчерпай все возможности существующей реализации
- Избегай внедрения новых паттернов или технологий без веского обоснования
- Если новые паттерны внедряются, убедись что старые реализации правильно удалены во избежание дублирования логики
- Поддерживай согласованность с существующими паттернами кодовой базы

## Организация кода

### Чистая кодовая база
- Держи кодовую базу очень чистой и организованной
- Следуй существующей структуре файлов и соглашениям по именованию
- Группируй связанный функционал вместе
- Удаляй неиспользуемый код и импорты

### Управление файлами
- Избегай написания одноразовых скриптов напрямую в файлах
- Если скрипты нужны, создавай их в соответствующих директориях (например, `scripts/`)
- Подумай, будет ли скрипт переиспользоваться, перед внедрением его в кодовую базу

### Лимиты размера файлов
- Держи файлы в пределах 200-300 строк кода
- Рефактори большие файлы, разбивая их на меньшие сфокусированные модули
- Разбивай сложные компоненты на меньшие составные части

## Рабочий процесс

### При создании нового кода:
1. Изучи существующую структуру проекта
2. Следуй установленным паттернам
3. Используй существующие библиотеки и утилиты
4. Не добавляй новые зависимости без необходимости

### При изменении кода:
1. Сначала прочитай и пойми существующий код
2. Сохраняй совместимость с остальными частями проекта
3. Следуй принципу минимальных изменений
4. Тестируй изменения перед финализацией

### При работе с шаблонами:
1. Каждый шаблон должен быть самодостаточным
2. Включай примеры использования
3. Документируй все параметры и опции
4. Предоставляй варианты для разных сценариев

### Батчинг изменений
- Где возможно делать массовые изменения - сначала анализируй что нужно изменить
- Затем меняй всё массово, чтобы сделать это максимально быстро
- Группируй похожие изменения для эффективности

## Работа с данными и тестирование

### Никаких фейковых данных в продакшене
- Моки данных допустимы только для тестов
- Никогда не добавляй stubbing или паттерны с фейковыми данными, которые влияют на dev или prod окружения
- Используй реальные источники данных и правильную обработку ошибок для разработки и продакшена

### Файлы окружения
- НИКОГДА не перезаписывай `.env` файлы без явного разрешения и подтверждения
- Всегда спрашивай перед изменением конфигурации окружения
- Делай бэкап существующих файлов окружения когда изменения необходимы

### Тестирование
- При тестировании запускай localhost на случайном порту от 3000 до 6000
- После завершения тестирования закрывай неиспользуемые порты, чтобы они не накапливались
- Создавай 5 комплексных тестов для каждого крупного компонента
- Тестируй как изолированную функциональность, так и интеграцию с существующими функциями
- Если какой-либо тест проваливается, устраняй проблему немедленно перед продолжением

## Безопасность

- НИКОГДА не сохраняй пароли, токены или ключи в коде
- Все конфиденциальные данные должны быть в переменных окружения
- Не логируй чувствительную информацию
- Всегда проверяй входные данные

## Логирование

### Основные принципы логирования
- Используй структурированное логирование через библиотеку winston
- Все логи сохраняются в файлы в директории `logs/`
- Error логи - в `logs/error.log`
- Все логи (info + error) - в `logs/combined.log`
- Ротация файлов по 10MB, хранение 14 дней

### Уровни логирования
- **ERROR** - только критические ошибки
- **WARN** - предупреждения о потенциальных проблемах
- **INFO** - ключевые операции (API запросы, сохранения в БД, webhook события)
- **DEBUG** - детальная отладочная информация (только в dev режиме)

### Что обязательно логировать
- **Все ошибки** - с полным стеком и контекстом
- **API запросы** - входящие и исходящие, с временем выполнения
- **Webhook события** - получение, обработка, результат
- **Операции с БД** - запросы, результаты, ошибки
- **OpenAI запросы** - модель, токены, стоимость, ошибки
- **Старт/завершение критических операций**

### Структура лога
```typescript
{
  level: 'info' | 'error' | 'warn' | 'debug',
  message: 'Описание операции',
  context: {
    requestId: 'abc123',
    userId?: 'user-id',
    timestamp: '2024-01-01T00:00:00.000Z'
  },
  data: {
    // специфичные данные операции
  }
}
```

### Использование
```typescript
import { log } from '@/lib/logging';

// Простое логирование
log.info('Операция выполнена');
log.error('Ошибка выполнения', { requestId: 'abc' }, { error: 'details' });

// Специализированные методы
log.webhook.received('Получен webhook', { source: 'upwork', payload: data });
log.api.request('API запрос', { method: 'POST', url: '/api/test' });
log.database.success('Сохранение в БД', { table: 'jobs', recordsCount: 5 });
log.openai.response('Ответ от OpenAI', { model: 'gpt-4', tokensUsed: 150 });
```

### Правила логирования
- Никогда не логируй пароли, API ключи или персональные данные
- Обрезай длинные тексты (>200 символов) для экономии места
- Всегда добавляй requestId для трейсинга запросов
- В production не используй debug уровень
- Контролируй размер логов - используй ротацию файлов
